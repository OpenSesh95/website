Fifteen Watts

Essays · 2026-11-17

There is a small computer in my house that draws fifteen watts. A desk lamp draws more. It is the always-on center of a personal build: five applied-AI projects, run under a hard cap of $100 a month, total, everything included.

The rest of the fleet is modest. An M1 MacBook. An iPhone and an iPad. An RTL-SDR radio, a cheap USB receiver that listens to whatever is in the air. When something needs real compute, I rent frontier cloud in short bursts and give it back. A zero-trust mesh ties it together, so no device is trusted because of where it sits on the network. Every connection proves itself. The little edge host is the citadel. The cloud is the weather.

I should say plainly what this is before anyone mistakes it for something bigger.

These are scaffolds. Contracts, skeletons, and green test suites, built contracts-first. I have not shipped five products. I have built five honest beginnings, and each one has a test suite that passes completely. A passing suite proves one thing: the system does what its contracts say. It does not prove the system is good, fast, or finished. That is the true size of the claim.

This is not an apology. It is the point.

My day job is enterprise data systems. At that scale, discipline is spread across teams, review gates, and runbooks written by people who left years ago. That spread is necessary, and it hides things. When a queue refuses bad input, you often can't say who decided it should, or why.

At fifteen watts you can hold the whole system in your head. There is nobody downstream to catch what I skip. So every discipline is visible, because every discipline is mine. Each constraint forced a decision I had to make out loud.

The first project is a retrieval engine that splits work between edge and cloud. Before I wrote a line of worker code, I wrote the contracts: the API spec for a query and the schema for the vector store. The workers came second, and they had to fit.

The order matters more than it sounds. When the contract comes first, the code has something to be wrong against. When the code comes first, the contract ends up describing whatever the code happened to do.

The chunker, which splits documents into pieces for retrieval, is deterministic. The same document produces the same chunks every time. That sounds like a small property until retrieval goes wrong and you need to know whether the data moved or the model did. If the chunker can drift, you can't tell. Eleven of eleven tests green.

The second project turns speech into structured tasks. You talk, and it produces something actionable. The queue has a floor: if a transcript comes in under 0.60 confidence, the pipeline will not extract tasks from it. The transcript is dead-lettered, set aside with its reason, and nothing acts on it.

The mechanism is simple. The reasoning is the part worth naming. A misheard sentence turned into a task is worse than no task, because acting is the expensive part. A missing task costs me a moment of noticing. A wrong task costs me the work of undoing something I never asked for. So the system refuses early, before the cost lands. Sixteen of sixteen tests green.

The third project fine-tunes models on rented spot GPUs. Spot capacity is cheap because the provider can take it back at any time. Under a $100 monthly cap, that tradeoff is the only reason this project can exist, and it shaped the entire design.

The center of the design is a budget gate. Every job carries a cost cap, with a default of $0.75 per burst. Before anything launches, the system projects the job's cost. If the projection exceeds the cap, the job is refused. No instance starts and no meter runs. The refusal happens where it is free.

The second decision is about preemption. When a spot instance gets reclaimed mid-run, the job is dead-lettered with its checkpoint location recorded. A resume picks up from that checkpoint, so it never pays again for work that already finished. Never pay twice is not frugality for its own sake. It is the difference between a budget that holds and one that leaks a little every time the world interrupts you. Fourteen of fourteen tests green.

The fourth project is an audio ML pipeline, and it taught me the difference between two kinds of failure.

A corrupt file will not improve. Retrying it is a bet that the world changed, and for a broken file the world didn't. So corrupt files dead-letter on the first failure, with the reason recorded. They are never retried forever and never silently dropped. Both of those are common, and both are lies. Retrying forever pretends the problem is temporary. Dropping silently pretends there was no problem.

There is one known transient failure, though, where the world really might change between attempts. That one gets a bounded retry of three attempts. The bound is the whole idea: hope gets a budget too. Thirteen of thirteen tests green.

The fifth project is the one I like most. It uses the RTL-SDR to pull aircraft telemetry out of the air: Mode S and ADS-B, the messages planes broadcast about who and where they are.

Here's the problem with testing a decoder. If I write the expected outputs from my own understanding of the format, my tests only prove I agree with myself. If I misread the spec, my code and my tests will be wrong together, and everything will be green.

So the decoder is verified against a recorded real-world frame, a public test vector with a published answer. It decodes to ICAO address 4840D6 and callsign KLM1023, exactly as published. That's the world grading my work instead of me grading it. Malformed frames are dead-lettered with their reason, like everywhere else in this build. Nine of nine tests green.

Put the five side by side and the same few decisions keep showing up.

Refuse early, before the cost is paid, whether that cost is money, compute, or a wrong action. Record reasons, so every refusal and every failure can explain itself later to the only person who will ask. Never pay twice: checkpoint, resume, and treat finished work as finished. Verify against the real world, because a test suite that only agrees with its author is a mirror.

None of these are new ideas. Every serious data system has some version of each one. But at enterprise scale they arrive as inherited policy, and the reasoning behind them rarely travels with them. On fifteen watts and a hundred dollars, I had to rediscover each one, because the constraint left me no choice.

That is my real argument. The frontier scales compute. You can rent more of it than you'll ever need, for a while. The edge teaches judgment. When the watts are fixed, the dollars are capped, and the labor is one person's evenings, every design choice becomes a choice you can see, defend, and price.

I've heard a lot of talk about sovereignty in AI lately, and much of it is a mood. Owning your stack, running local, getting out from under the platforms. I'm sympathetic, but a mood isn't an architecture.

Sovereignty, as I've come to understand it, is concrete. It is a system that answers to you. It runs in your house, on your power budget. When something refuses, fails, or resumes, the person who built it can explain why, end to end, without asking anyone.

That's all these five scaffolds are. They are small and honest about their size, and every line of them can be explained.

Fifteen watts turns out to be enough for that.
